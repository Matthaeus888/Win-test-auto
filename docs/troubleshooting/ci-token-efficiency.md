# 토큰 절약을 위한 아이디어와 구현

이 프로젝트는 Claude Code(AI 에이전트)가 CI 상태를 직접 조회·진단하며 작업하는
구조라, "GitHub Actions 실행 비용"뿐 아니라 **AI 에이전트가 상태를 확인하는 데
쓰는 대화 토큰**도 함께 아껴야 하는 특이한 최적화 대상이 있다. 실제로 이 저장소의
CI를 디버깅하는 과정에서 비효율이 관찰되었고, 이를 계기로 두 축으로 개선했다.

## 배경: 무엇이 비효율이었나

새 저장소로 이전 후 GitHub Secrets 설정 문제(→
[ci-secrets-setup.md](./ci-secrets-setup.md))를 진단하는 동안, CI 실행 완료를
확인하기 위해 **15초 간격으로 20~26회씩 GitHub API를 반복 폴링**하는 패턴이
여러 차례 발생했다. Selenium E2E 스위트는 최소 5분 이상 걸리므로, 15초 간격
폴링은 대부분 "아직 실행 중"이라는 동일한 응답만 반복해서 받는 결과로 이어져
대화 토큰을 불필요하게 소모했다. 또한 문서(README 등)만 수정한 커밋도 매번
전체 테스트 스위트를 트리거해, CI 실행 자체도 불필요하게 반복됐다.

## 1) GitHub Actions 트리거 최적화 (`ci.yml`)

### `paths-ignore`로 문서 전용 변경은 CI 대상에서 제외

```yaml
on:
  push:
    branches: [master]
    paths-ignore:
      - '**.md'
      - 'docs/**'
      - 'LICENSE'
```

README나 `docs/` 아래 문서만 수정한 커밋은 애초에 Selenium 스위트를 돌릴
이유가 없다. 이 저장소는 Public이라 GitHub Actions 실행 시간 자체는 무료지만,
불필요한 5~10분짜리 실행이 반복되면 (1) Actions 탭의 신호 대 잡음 비율이
나빠지고 (2) AI 에이전트가 "방금 그 실행이 문서 커밋 때문인지 코드 커밋
때문인지" 매번 다시 확인해야 하는 부가 비용이 생긴다. `schedule`/
`workflow_dispatch` 트리거는 `paths-ignore`의 영향을 받지 않으므로(공식 문서
기준 `push`/`pull_request` 트리거에만 적용됨), 매일 스케줄 실행이나 수동 실행은
그대로 유지된다.

### `concurrency`로 연속 push 시 이전 실행 자동 취소

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.event_name }}-${{ github.ref }}
  cancel-in-progress: true
```

같은 브랜치에 짧은 간격으로 커밋을 연달아 push하면(디버깅 중 흔한 패턴), 이전
실행은 어차피 최신 커밋 기준으로 다시 실행해야 하므로 의미가 없어진다.
`cancel-in-progress: true`로 이전 실행을 자동 취소해, 마지막 커밋에 대한 결과만
남긴다. `group` 키에 `github.event_name`을 포함해 `schedule` 실행끼리는 서로
취소하지 않도록 분리했다(매일 스케줄 실행이 다른 스케줄 실행을 취소하면 안 되기
때문).

## 2) AI 에이전트의 CI 모니터링 방식 개선 (실행 방식 원칙)

코드로 표현되지는 않지만, 이 프로젝트에서 Claude Code가 CI를 확인할 때 따르는
원칙도 함께 정리한다(향후 이 저장소에서 작업하는 세션이 참고하도록 문서화).

- **폴링 간격은 예상 실행 시간에 맞춘다**: 5분 걸리는 작업을 15초 간격으로
  확인하지 않는다. 과거 실행 이력(예: 이 스위트는 통상 5~6분)을 근거로 최소
  1~2분 이상의 간격을 둔다.
- **필요한 정보만 추출한다**: 로그 전체를 대화에 그대로 붙여넣지 않고, API
  응답에서 스텝 상태·annotations 등 **판단에 필요한 필드만 파싱**해서 확인한다
  (`docs/troubleshooting/ci-secrets-setup.md`에서 실제로 이렇게 원인을 좁혔다).
- **접근 제한은 빨리 인정하고 사람에게 넘긴다**: 관리자 인증이 없어 로그 원문을
  가져올 수 없는 상황이라면, 추가로 여러 API를 시도해보며 토큰을 쓰는 대신
  일찍 한계를 인정하고 사용자에게 캡처를 요청하는 것이 더 효율적이다.
- **PR 기반 워크플로우에서는 캐시된 상태 조회를 우선한다**: 이 프로젝트처럼
  `master`에 직접 push하는 구조가 아니라 PR 기반으로 작업한다면, CI 상태를 알기
  위해 매번 GitHub API를 폴링하는 대신 Claude Code 앱이 이미 캐싱해 둔 PR/CI
  상태 조회 기능을 우선 활용하는 것이 더 적은 요청으로 같은 정보를 얻는
  방법이다.

## 요약

| 축 | 적용 전 | 적용 후 |
|---|---|---|
| 문서만 바뀐 커밋 | 매번 전체 Selenium 스위트(5~10분) 실행 | CI 트리거 자체를 건너뜀 |
| 연속 push | 이전 실행들이 끝까지 실행되며 리소스 낭비 | 최신 커밋만 남기고 이전 실행 자동 취소 |
| AI 에이전트의 CI 확인 | 15초 간격 반복 폴링, 로그 전체 조회 시도 | 예상 소요시간 기반 간격, 필요한 필드만 조회, 조기에 한계 인정 |
