# 트러블슈팅: Flaky 테스트 대응 원칙과 실전 사례

Selenium 기반 E2E 테스트는 실제 프로덕션 사이트를 대상으로 하기 때문에, 코드가 아닌
외부 요인(네트워크, 제3자 광고, 서버 응답 지연 등)으로 인한 간헐적 실패가 발생할 수
있다. 이 문서는 "실패하면 일단 재시도해서 통과시킨다"는 안이한 방식 대신, **원인을
구분하고 각 원인에 맞게 대응**한 실제 사례를 정리한다.

## 원칙: 실패 원인을 4가지로 구분한다

[`CLAUDE.md` 13절](../../CLAUDE.md)에 따라 모든 테스트 실패는 아래 4가지 중 하나로
분류를 시도하며, **불명확하면 추측으로 결론짓지 않고 보고한다.**

| 원인 | 정의 | 대응 |
|---|---|---|
| Automation Code | 테스트/Page Object 코드 자체의 버그 | 코드 수정 |
| Test Data | 테스트 계정/입력값 등 데이터 문제 | 데이터 수정 |
| Test Environment | 실행 환경(브라우저, CI, 네트워크) 문제 | 환경 설정 수정 |
| 실제 Product 문제 | 대상 서비스 자체의 결함 | [결함 리포트](../defects/README.md)로 기록, 코드는 수정하지 않음 |

**금지 사항**: 실패를 회피하기 위한 무한/반복 재시도, 원인 불명 상태에서의 임의 PASS
처리.

## 사례 1: 헤드리스(CI) 환경에서만 발생한 `maximize_window()` 결함

**증상**: 로컬(headed) 환경에서는 문제없던 테스트가 GitHub Actions(headless Chrome)
환경에서 뷰포트 관련 요소를 찾지 못해 실패.

**원인**: `driver.maximize_window()`가 headless 모드에서는 브라우저 창을 최대화하는
대신 기본 크기(800×600)로 축소시키는 것으로 실측 확인됨.

**대응**: `conftest.py`의 `driver` fixture에서 `CI` 환경변수로 headless 여부를 감지해,
headless일 때는 `maximize_window()` 호출을 생략하고 대신 명시적으로 큰 해상도를
`--window-size`로 지정하도록 분기 처리.

## 사례 2: CI 워크플로우의 조건식 논리 오류로 Slack 알림이 영원히 실행되지 않음

**증상**: 테스트가 실패해도 Slack 알림 스텝이 실행되지 않음.

**원인**: `.github/workflows/ci.yml`에서 pytest 실행 스텝에 `continue-on-error: true`를
설정해 이후 스텝(리포트 업로드 등)이 계속 진행되도록 했는데, Slack 알림 스텝의 조건을
`if: failure()`로 지정했다. `continue-on-error: true`가 걸린 스텝은 실패해도 **워크플로우
전체를 "성공"으로 간주**하기 때문에, `failure()` 컨텍스트가 결코 참이 되지 않아 알림
스텝이 논리적으로 영원히 실행 불가능한 상태였다.

**대응**: `if: failure()` 대신 `if: steps.run_tests.outcome == 'failure'`로 변경 —
`continue-on-error`와 무관하게 해당 스텝 자체의 실제 성공/실패(`outcome`)를 직접
참조하도록 수정.

## 사례 3: 알려진 Production 결함과 새로운 실패를 구분하기

[DEF-001](../defects/DEF-001-logout-session-not-terminated.md)처럼 이미 알려진 간헐적
Product 결함이 있는 경우, 다음에 같은 테스트가 또 실패했을 때 "어차피 알려진 결함이니
PASS 처리"로 넘기고 싶은 유혹이 생긴다. 이 프로젝트에서는 아래 원칙을 지켰다.

1. 실패할 때마다 **스크린샷/응답 상태를 다시 확인**해 정말 같은 원인인지 검증한다
   (다른 원인일 수도 있으므로).
2. 검증 전까지는 계속 **FAILED로 보고**하며, Assertion을 완화하거나 자동으로 넘기지
   않는다.
3. 로컬(headed)과 CI(headless) 양쪽에서 재현되는지 교차 확인해, 특정 환경의 문제가
   아니라 실제 대상 서비스의 문제임을 배제법으로 좁힌다.

## 사례 4: 광고 오버레이로 인한 연쇄 실패

제3자 광고 개입으로 인한 클릭 가로채임은 별도 문서
[ad-overlay.md](./ad-overlay.md)에 상세히 정리되어 있다 — 최적화를 먼저 적용했다가
실측 없이 판단해 오히려 회귀를 유발했던 사례를 포함한다.

## 요약: 이 프로젝트의 Flaky 대응 철학

- **재시도는 결정적 횟수 제한**을 둔다(무한 재시도 금지).
- **재시도해도 안 되면 원인을 구분**한다 — "환경 문제려니" 하고 넘기지 않는다.
- **같은 증상이 반복돼도 매번 재검증**한다 — 한 번 결함으로 판정했다고 이후 발생하는
  모든 유사 실패를 자동으로 같은 결함으로 단정하지 않는다.
- 결정적 판정이 어려운 경우 **추측 대신 사용자(또는 팀)에게 보고**한다.
